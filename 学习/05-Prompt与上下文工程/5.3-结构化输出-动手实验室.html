关卡 1

两条管道：同一段输出，两种命运

验收：模型输出没有固定格式——它吐什么完全由你的 prompt 决定；决定"要不要 parse"的是收件人。

先破一个错的前提："模型输出的本来就不是格式化的东西"。错。模型是"文本进、文本出"的函数，它吐什么形状完全由你要求。你说"聊聊天气"它吐散文；你说"把笔记整理成 JSON"，它吐的就是 JSON 长相的文本——JSON 本身也只是 14 个普通字符，不是什么"格式化容器"。

下面是同一场会议、同一个模型、同一个输出，只是收件人不同。点按钮看两种读法各自的下场：

模型的真实输出（就是一段文本，两边拿到的是同一份）：

好的，以下是整理好的会议记录： ```json { "title": "周会", "actionItems": [ { "owner": "小李", "task": "修导出闪退", "due": "周五前" } ] } ``` 希望对你有帮助！

🧑 管道 A：渲染给人看（聊天页）

读法：Markdown 渲染器 + 人眼

【Markdown 渲染结果】 客套话 —— 原样显示 "json" —— 渲染成代码块，还带高亮 {...} —— 原样显示在代码块里 客套话 —— 原样显示 👤 用户看到：格式清晰的一份会议记录 ✓

🤖 管道 B：当数据用（你的程序）

读法：JSON.parse(输出)

const obj = JSON.parse(模型输出); // ↑ 第一个字符是"好"，不是 { // 💥 SyntaxError: Unexpected token '好' // 程序当场死亡，后续代码一行都不执行

↓ 同一份输出，管道 A 是满分答卷，管道 B 是死刑判决。输出没变，变的是读它的东西。这就是"吐散文 vs 吃 JSON"的全部含义。

📝 为什么聊天让人产生"不需要 parse"的错觉你在聊天页看到的 content 确实只给人看——但那是因为聊天应用在 content 之前就把信封拆完了（res.json() / SSE 的 JSON.parse），content 本身恰是唯一不用再 parse 的字段。而 5.3/5.4 讲的是让 content 也变成程序可读的数据——那是 Agent 的主干道。

关卡 3

双胞胎：JSON Schema 与 Zod

验收：JSON Schema 是格式标准（给模型看的说明书）；Zod 是 npm 库（给程序用的验收员）。同一结构，两份写法。

关卡 2 的结论：模型输出 90% 是好的，10% 会毁一切。工程解法不是祈祷那 10% 别发生，是两头加设施——出口跟模型说清"要什么形状"，入口跟程序说清"什么算对"：

出口设施：JSON Schema —— 不是库，是格式标准

一份"用 JSON 描述 JSON"的公开规范。它没有代码、不装包，你手写一个对象字面量就在用它。类比 OpenAPI 之于 HTTP 接口。

{
  "type": "object",
  "properties": {
    "owner": { "type": "string" },
    "due":   { "type": ["string","null"] }
  },
  "required": ["owner","due"]
}

塞进 prompt 或 response_format 发给模型 → 模型照着形状交货。厂商服务器用它做约束解码，你的代码里它只是一份数据。

入口设施：Zod —— 是库，npm i zod

TS/JS 库，用代码声明同样的结构，一次给你两样：编译期类型 + 运行时校验。类比：能跑的 TypeScript 类型。

const S = z.object({
  owner: z.string(),
  due:   z.string().nullable(),
});
type M = z.infer<typeof S>; // 类型
S.safeParse(data);          // 校验

TS 类型编译后就蒸发，运行时没东西替你查 API 吐回的对象 → Zod = 类型的运行时形态。

📝 为什么要两份收件人不同：Schema 的读者是模型（它只认识 prompt 里的文本），Zod 的读者是你的程序（它只认识运行时对象）。同一个"会议记录"结构，说给两个完全不同的听众听。重复很蠢 → Vercel AI SDK 能从 Zod 自动导出 JSON Schema，写一份两处用——第 6 章的福利。

Zod 试驾：语法对 ≠ 形状对

验收：JSON.parse 只查语法；Zod 查形状（字段/类型/可空）。样本 5 那种"语法合法的错货"只有 schema 层能拦。

自愈循环：失败不是终点，是下一轮的输入

验收：parse/Zod 失败不抛给用户——把错误喂回模型让它自己修。循环体在你的代码里。

前三关全部是"失败长什么样"。工程上最优雅的一步：失败不抛给人，喂回模型——它知道自己刚才输出了什么，把 Zod 的报错贴给它，它改得比你还快。5.3 脚本的 tidy() 就是个最多两轮的循环：

通关自测（点开对照）

Q1：模型输出的收件人有谁？谁决定要不要 parse？
人或代码——由应用形态决定：聊天页给人（不 parse content）；提取器/Agent 给代码（parse 是主干道）。输出本身两边拿到的同一份。
Q2：JSON.parse 的一条铁律？三个最常见的死因？
整串必须恰好是一个合法 JSON 值，从第一个字符开始。死因：围栏（```）、客套话、中文标点——全是模型对训练语料的忠实复刻。
Q3：JSON Schema 和 Zod 分别是库吗？各写给谁？
JSON Schema 不是库，是格式标准（给模型看，塞 prompt / response_format）；Zod 是 npm 库（给程序用，safeParse + z.infer）。
Q4：语法合法但形状不对，parse 拦得住吗？谁拦？
拦不住。parse 只查语法；形状（字段/类型/可空）由 Zod 在运行时查——它是"类型的运行时形态"。
Q5：校验失败后工程上最优雅的动作？谁握方向盘？
不抛给用户，把错误信息 push 进 messages 喂回模型让它修（self-heal），设轮次上限防死循环。方向盘全程在你的代码：fetch、safeParse、messages.push 都是你在驱动。
Q6：Zod 能查出"owner 值是编造的"吗？
不能——它能查类型不能查事实。语法可校验、事实不可校验，编造的值是幻觉（4.8）在结构化世界的变身，防线在下游（人工确认）。
