8.1

Workflow vs Agent 的边界

验收：两者的判定标准？为什么 Anthropic 说"多数场景答案=工作流"？记法 Agent = LLM + 记忆 + 工具 + RAG + MCP + Skills。
💡 钩子先泼冷水：Anthropic 那篇必读文章的核心结论不是"怎么做 Agent"，而是"能用工作流就别用 Agent"。Agent 的自由度是拿可靠性换的——每多一分让模型自主决策，就多一分失控面。学 Agent 的第一课是知道什么时候不用它。

判定标准：谁决定控制流

Workflow（工作流）Agent（智能体）
控制流你的代码预先编排（先 A 后 B 再 C，分支你写死）模型自己决定下一步（循环里模型说了算）
LLM 的角色流水线上的工人（按工序干活）拿着工具箱的承包商（自己安排工序）
可预测性高——同样输入基本同样路径低——路径随模型判断漂移
成本/延迟可预算不可预算（轮数不定）
适合结构固定的任务（翻译→审校→发布）开放任务（"修好这个 bug"、"调研并写报告"）
📝 用你的项目验证chat-app 的 route.ts 是工作流还是 Agent？——它有 tools + stopWhen，模型能自主决定调不调工具、调几次——已经是萌款 Agent（单工具的受限 Agent）。而 5.3 的四档实验台是纯工作流（固定管线）。你其实两样都写过了，这一节只是给它们正名。

记法：Agent = LLM + 记忆 + 工具 + RAG + MCP + Skills

这不是定义，是零件清单——每项你都有对应库存：

零件作用你的库存
LLM决策引擎4 章（模型怎么想）
记忆短期历史 + 长期事实5.5（压缩三板斧）+ 8.5（本章展开）
工具伸向世界的手段5.4（四步协议）+ 8.3（本章设计学）
RAG外挂知识第 7 章整章
MCP工具的标准化插座8.7（本章动手写 server）
Skills技能包按需加载8.9（本章【浅】）

而把这些零件串起来的那根轴，就是 8.2 的 Agent Loop——while 循环 + 决策 + 执行 + 观测。先写它，再逐个精修零件。

🔧 动手 8.1（纸面，15 分钟）列出你毕业项目想做的 3 个功能，逐个判定"工作流还是 Agent"，写判定理由（控制流该谁定？失败重试的代价？）。预期发现：至少一个你原以为是 Agent 的功能，其实是工作流更合适——这就是 Anthropic 那篇文章想教你的判断力。
8.2

Agent Loop（ReAct）——手写一遍 ⭐

验收：~100 行 TS 裸写 while 循环：工具注册表 + 终止条件 + 历史管理 + 并行工具调用。这是全路线最重要的练习。
💡 钩子你 5.4 已经写过这个循环的雏形（read_file 工具四步往返）——8.2 是它的完全体：从"单工具单任务"升级为"多工具、并行调用、历史管理、条件终止"的真 Agent。不用任何框架——框架是给已经懂循环的人省时间的，你现在自己写一遍，将来读任何框架源码都是"哦，这就是我那个 while"。

ReAct：循环的心智模型

ReAct = Reason + Act（推理+行动交替）：模型每轮先"想"（我需要什么信息/该做什么），再"动"（调工具），观察结果，再想再动……直到认为任务完成。这个模式不需要你写任何特殊 prompt——Function Calling 协议天然就是 ReAct：tool_calls 是"想+动"，role:"tool" 回喂是"观察"，finish_reason:stop 是"完工"。你已经亲眼见过它跑（5.4 实验台 + chat-app），现在把它写完整。

完整骨架（~100 行，五大件）

import "dotenv/config";
import { readFileSync, writeFileSync } from "node:fs";
import path from "node:path";

const BASE_URL = (process.env.LLM_BASE_URL ?? "https://api.deepseek.com").replace(/\/+$/, "");
const API_KEY = process.env.LLM_API_KEY ?? "";
const MODEL = process.env.LLM_MODEL ?? "deepseek-chat";

// ── 五大件之一：工具注册表（name → 说明书 + 执行器）──
// 说明书给模型看（8.3 讲怎么写好），执行器是你的代码（安全边界在这）
type ToolDef = {
  description: string;
  parameters: object;                       // JSON Schema
  execute: (args: any) => Promise<string>;  // 统一返回字符串（回喂协议）
};

const tools: Record<string, ToolDef> = {
  read_file: {
    description: "读取 data/ 目录下的文本文件。只允许 data/ 内的文件。",
    parameters: { type: "object", properties: { filename: { type: "string" } }, required: ["filename"] },
    execute: async ({ filename }) => readFileSync(path.join("data", path.basename(filename)), "utf8"),
  },
  write_file: {
    description: "把文本写入 data/ 目录下的文件（覆盖）。用于保存整理结果。",
    parameters: { type: "object", properties: { filename: { type: "string" }, content: { type: "string" } }, required: ["filename", "content"] },
    execute: async ({ filename, content }) => {
      const safe = path.basename(filename);
      writeFileSync(path.join("data", safe), content, "utf8");
      return `已写入 ${safe}（${content.length} 字符）`;
    },
  },
  list_files: {
    description: "列出 data/ 目录下所有文件名。",
    parameters: { type: "object", properties: {} },
    execute: async () => readFileSync === null ? "" : (await import("node:fs")).readdirSync("data").join("\n"),
  },
};

// 说明书清单（发给模型的 tools 参数，从注册表自动生成——单一事实来源）
const toolsForApi = Object.entries(tools).map(([name, t]) => ({
  type: "function",
  function: { name, description: t.description, parameters: t.parameters },
}));

// ── 五大件之二：LLM 调用（和 5.4 相同，无新东西）──
async function callLLM(messages: any[]) {
  const res = await fetch(`${BASE_URL}/chat/completions`, {
    method: "POST",
    headers: { "Content-Type": "application/json", Authorization: `Bearer ${API_KEY}` },
    body: JSON.stringify({ model: MODEL, messages, tools: toolsForApi, temperature: 0 }),
    signal: AbortSignal.timeout(120_000),
  });
  const j = await res.json();
  if (!res.ok) throw new Error(`HTTP ${res.status}: ${JSON.stringify(j)}`);
  return j.choices[0].message;
}

// ── 五大件之三+四+五：主循环（终止条件 / 历史管理 / 并行执行）──
async function runAgent(task: string, maxRounds = 10) {
  const messages: any[] = [
    { role: "system", content: "你是文件助手，用中文。用提供的工具完成任务；完成后简短汇报。" },
    { role: "user", content: task },
  ];

  for (let round = 1; round <= maxRounds; round++) {
    console.log(`\n── 第 ${round} 轮 ──`);
    const assistantMsg = await callLLM(messages);
    messages.push(assistantMsg);                       // 历史管理：意图原样进剧本

    if (!assistantMsg.tool_calls?.length) {
      return assistantMsg.content;                     // 终止条件①：模型认为完工
    }

    // 并行工具调用：一轮里多个 tool_calls 全部执行（Promise.all）
    // 注意：回喂顺序必须与 tool_calls 顺序一致（协议要求 tool_call_id 对上）
    const results = await Promise.all(assistantMsg.tool_calls.map(async (call: any) => {
      const name = call.function.name;
      const tool = tools[name];                        // 查注册表——模型只能调注册过的
      if (!tool) return { id: call.id, out: `错误：工具 ${name} 不存在` };
      try {
        const args = JSON.parse(call.function.arguments || "{}");
        console.log(`  🔧 ${name}(${JSON.stringify(args)})`);
        const out = await tool.execute(args);
        console.log(`  ✓ ${String(out).slice(0, 80)}...`);
        return { id: call.id, out };
      } catch (e: any) {
        console.log(`  ✗ ${e.message}`);
        return { id: call.id, out: `执行失败：${e.message}` };  // 失败也回喂（5.4 教训）
      }
    }));
    for (const r of results) {
      messages.push({ role: "tool", tool_call_id: r.id, content: r.out });
    }
    // 循环继续 → 带着新观测重新请求
  }
  return "（已达最大轮数，硬停）";                       // 终止条件②：保险丝
}

// 跑一个真实小任务
const answer = await runAgent(
  "看看 data 目录里有哪些文件，读一下 todo.md，把『本周』的任务整理成 clean-week.md 保存。"
);
console.log("\n═══ 最终回答 ═══\n" + answer);

和 SDK 的关系（6.3 遗留问题的正式答案）

现在你能精确说出 stopWhen: stepCountIs(5) 替你干了什么了：就是这个 while + 注册表查漏 + Promise.all 并行 + 按 id 回喂。SDK 版适合"标准循环"；手写版的价值：①循环里可以插任何自定义逻辑（每轮渲染进度、人工审批、动态换模型——8.15 的交互设计全靠这个口子）；②出问题时你看得见每一行。毕业项目建议：8.2 手写版直接演化成毕业项目的内核（你的场景要人工确认弹窗，手写循环是刚需），SDK 版 chat-app 留作聊天壳。

8.3

工具设计：给模型用的 API 设计

验收：description 怎么写才"可执行"？参数怎么定？错误信息为什么是给模型看的提示而非堆栈？
💡 钩子工具设计 = API 设计的分支学科，但读者从人类程序员换成了概率模型。人类读文档会猜、会查源码；模型只读你的 description 和参数 schema——写得含糊，调用就含糊；写得精确，Agent 就靠谱。工具质量是 Agent 质量的第一杠杆（比换模型还灵）。

description 四要素（可执行的说明书）

要素反面教材正面教材
做什么"文件工具""读取 data/ 目录下文本文件的内容"
边界（防误用）（不说，模型乱传路径）"只允许 data/ 内的相对文件名"
何时用（模型自己猜）"当用户提到查看某个笔记/文件内容时"
何时不用于何（沉默）"不要用它读 data/ 以外的路径；搜索笔记内容用 search_notes"

要点：和别的工具划清地盘。模型在多个工具间选择时，description 是它唯一的决策依据——两个工具职责重叠，就会随机乱选（8.12 的经典失败模式）。

参数设计三条

  • 少而精：每个参数都要过一遍"模型能从对话上下文推断出来吗"——能推断的删掉。参数越多，填错的自由度越大
  • 枚举 > 自由字符串：mode: enum["full","summary"] 远好于 mode: string——schema 即文档即校验（5.3 的老朋友）
  • 示例进 description：格式敏感的参数（如路径写法），在 description 里给正例："如 todo.md；不要带目录前缀"

错误信息：给模型的提示，不是给程序员的堆栈

// 反面：模型看到这个只会重试同样的调用
执行失败：Error: ENOENT: no such file or directory, open 'C:\Users\...\data\todo.md'

// 正面：模型看到这个会自己修正
执行失败：文件 todo.md 在 data/ 目录不存在。可用文件：todo.md, clean-week.md（可用 list_files 查看）

你在 5.4 实验台见过实证：执行器返回 ENOENT 时模型如实转告但不知所措——因为错误信息没给它"下一步"。**好错误信息 = 发生了什么 + 为什么 + 模型现在该怎么改**（三个都有，模型的自愈率直线上升）。

🔧 动手 8.3（随 8.2 做）给 8.2 的三个工具各写两版 description（一版含糊、一版按四要素），各自跑同一个任务三次，对比工具选择的稳定性——把差异记进笔记。这就是"工具质量是 Agent 质量第一杠杆"的实测。
8.4

规划与反思

验收：先规划再执行 vs 边走边看的取舍？Reflection 在循环里怎么落？三个经典范式各一句话。
💡 钩子8.2 的循环是"边走边看"（ReAct 默认）：每轮只决定下一步。任务一复杂（十几个步骤、有依赖），它会在第 6 步忘掉第 1 步的目标。规划 = 给循环加一张地图——但地图本身也是成本，不是所有任务都值得画。

两种策略的取舍【精】

先规划再执行（Plan-then-Execute）边走边看（ReAct 默认）
做法第一步先让模型产出计划（结构化，5.3 的 schema），逐步执行直接进循环，每轮看情况决策
优势长任务不迷路；计划可预览可审批（8.15 交互设计的抓手！）零额外成本；短任务更快
劣势计划可能基于错误假设（执行中发现要重规划）长任务漂移、忘目标、来回兜圈
适合步骤多、有依赖、可预见（"整理全部笔记生成索引"）步骤少、探索性强（"看看 todo 里有什么"）

工程正解是混合：简单任务直接 ReAct；复杂任务先出计划（并展示给用户确认——毕业项目的"计划预览"功能就是它）→ 执行 → 偏离时允许重规划。判定线和 8.1 一样：控制流的自由度给多少，看任务的复杂度与可逆性。

经典范式三句话【浅】

  • Plan-and-Solve：先产出完整计划再逐步执行——上面的"先规划"的学术名
  • Reflection：行动后让模型自我批评（"刚才的结果哪里可能不对？"）再修正——落进循环里就是"每 N 轮插一次反思 prompt"或"完工前自查一轮"；成本是额外轮次，换复杂任务的成功率
  • ToT（思维树）：同时探索多条思路分支再择优——研究性场景用，工程上很少真做（分支=成本指数化），知道即可
🔧 动手 8.4（随 8.2 做）给 8.2 的 agent 加"计划模式"：system 里要求"收到多步任务时，第一个回复只输出编号计划等用户确认"——跑一个 5 步任务，观察：计划质量如何？执行时它遵守计划吗？偏离时你能从轨迹里看出来吗？（这就是毕业项目"计划预览"功能的原型。）
8.5

记忆

验收：短期记忆=什么、三策略？长期记忆的落地形态？毕业项目各用哪种？
💡 钩子Agent 的"记忆"没有任何魔法：短期记忆 = messages 数组（5.1 剧本）；长期记忆 = 一个你设计的存储 + 检索方案（7 章 RAG 的复用）。所有"AI 有记忆"的产品宣传，拆开都是这两样。

短期记忆【精】：messages 的管理

循环跑得越久，messages 越肥——工具结果是大头（一次 read_file 就几千字符）。肥历史 = 每轮全量重发的成本 + 5.5 的 lost in the middle。三个策略（5.5 压缩三板斧的 Agent 场景复述）：

策略做法取舍
窗口截断只留最近 N 轮 + system + 任务目标最便宜；会忘早先约束——补救：把任务目标常驻 system（不随截断丢）
工具结果剪枝老的工具输出替换成一行摘要（"已读取 todo.md，要点：6 项待办"）性价比之王：原文用了就过时，摘要足够续命
摘要压缩（compaction）接近窗口上限时，把老历史整体碾成一段摘要替换Anthropic 长文的核心招；细节可能丢，摘要本身要烧一次调用

你的 agent-lab 起步版可以不管理（任务短）；一旦跑长任务（十几轮）就会亲历"越跑越贵+开始忘事"——那时回来上第二招。

长期记忆【浅】：落地形态

形态一句话适合
向量记忆事实/对话片段 embedding 入库，按语义检索——就是第 7 章 RAG 换了个名字"用户上次说过…"
结构化卡片把事实抽成字段存（用户名/偏好/项目状态），每轮拼进 system少而精的硬事实（8.5 之前聊过的"结构化记忆"）
知识图谱 / Mem0 类实体关系图或专用记忆服务，自动抽取+更新+遗忘记忆密集型产品；毕业项目暂不需要，知道即可

毕业项目的取舍：短期=剪枝+常驻任务目标；长期=结构化卡片起步（桌面助手要记住的不多：常用路径、偏好、上次任务）——向量记忆等第 7 章知识库做完了顺手就有了。

🔧 动手 8.5（轻量）给 8.2 的 agent 人为制造一次"变胖"：任务要求它读 5 个文件再总结——观察 messages 字节数每轮涨多少；然后实现最简剪枝：第 6 轮起把已完成工具的结果替换成"[已读取 xxx.md，要点略]"——对比前后的 token 消耗（日志里有 usage）。
8.6

多智能体

验收：编排者-工作者/Handoff/子 Agent 三模式各自的样子？何时不该拆？
💡 钩子先把冷水泼在前头（Anthropic 文章的另一核心）：多智能体是"必要的复杂度"，不是"架构的排场"。多个 Agent = 多份 context = 沟通成本和失控面平方级增长——单 Agent 能干的活拆多 Agent，纯属自找麻烦。

三种模式

编排者-工作者（Orchestrator-Workers）

  • 一个主管 Agent 拆任务 → 派发给多个工人 Agent → 汇总
  • 典型：Deep Research 型——主管拆"调研 A/B/C 三块"，工人各自检索写作，主管汇总成报告
  • 你的 loop 就是工人模板；主管=另一个调 runAgent 的 loop

Handoff（接力）

  • Agent A 干到某步把控制权整个交给 Agent B（带上下文交接）
  • 典型：客服分诊——一线 Agent 判断问题类型，转交退货专员/技术专员
  • OpenAI Agents SDK 的核心原语就是这个

子 Agent（隔离上下文）

  • 主 Agent 往"黑盒"里丢一个任务，只收回结论——子 Agent 的几十轮脏活不污染主上下文
  • 本质是"用子 Agent 当上下文过滤器"——8.5 记忆问题的另一种解
  • 你将来读 Claude Code 的 Task 工具，就是这个

何时不该拆（判断清单）

  • 任务能在一个循环里 10 轮内干完 → 不拆（单 Agent + 好工具更可靠）
  • 拆的动机是"听说多智能体厉害" → 不拆（动机不纯）
  • 各子任务上下文天然隔离（调研三个互不相干的主题）→ 该拆（收益明确）
  • 单 Agent 上下文已经爆了（8.5 三策略都救不动）→ 该拆（子 Agent 当上下文过滤器）
8.7

MCP 与互操作协议

验收：MCP 解决什么问题？server/client 各干什么？动手写一个 MCP server 并接进自己的 loop。A2A/ACP/ANP 知道分工。
💡 钩子你 8.2 的工具注册表有个隐形天花板：每个 Agent 都要自己实现一遍 read_file。MCP（Model Context Protocol，Anthropic 2024 开源）干的事就是把"工具"标准化成协议——任何人写的 MCP server，任何支持 MCP 的 Agent 都能直接用。类比：USB。之前每个外设配专用接口，USB 之后插上就能用。

原理：三个角色

角色干什么类比
MCP Server暴露工具：声明工具清单（name/description/schema）+ 实现执行USB 设备（鼠标/键盘/U盘）
MCP Client连接 server、拉取工具清单、转发调用电脑的 USB 口
Agent（宿主）把拉来的工具挂进自己的工具注册表操作系统
关键映射：MCP 工具清单 ≈ 你 8.2 的 toolsForApi；MCP 工具调用 ≈ 你的 execute()——协议换了，Agent Loop 一行不改

传输层两种：stdio（本地子进程，桌面应用主用）和 Streamable HTTP（远程服务）。Claude Desktop 里配的那些"插件"就是本地 MCP server 子进程。

动手：写一个 MCP server（README 指定）

// mcp-notes-server.ts —— "搜索我的学习笔记" server
// npm i @modelcontextprotocol/sdk zod；跑：npx tsx mcp-notes-server.ts
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";
import { readFileSync, readdirSync } from "node:fs";
import path from "node:path";

const server = new McpServer({ name: "notes-search", version: "1.0.0" });

server.tool(
  "search_notes",                                   // 工具名
  "在学习仓库的 md 文件里搜索关键词，返回命中文件与行",
  { keyword: z.string().describe("要搜的关键词，如 MCP / chunking") },
  async ({ keyword }) => {
    const hits: string[] = [];
    const walk = (dir: string) => {
      for (const f of readdirSync(dir, { withFileTypes: true })) {
        const p = path.join(dir, f.name);
        if (f.isDirectory()) walk(p);
        else if (f.name.endsWith(".md")) {
          readFileSync(p, "utf8").split("\n").forEach((line, i) => {
            if (line.includes(keyword)) hits.push(`${p}:${i + 1}: ${line.trim().slice(0, 80)}`);
          });
        }
      }
    };
    walk("../../学习");                              // 相对启动目录
    return { content: [{ type: "text", text: hits.slice(0, 20).join("\n") || "无命中" }] };
  },
);

await server.connect(new StdioServerTransport());   // stdio 模式：被宿主当子进程拉起

验证路径两条：①接进 Claude Desktop（配置文件里注册这个 server，重启即可对话使用）；②接进你自己的 loop——写个 MCP client 拉取工具清单转成 8.2 的注册表格式（@modelcontextprotocol/sdk/client，约 30 行）。第二条更能验证"协议换了循环不改"。

生态与兄弟协议【了】

  • MCP 生态现状：官方 servers 仓库（文件系统/GitHub/Slack 等现成的）+ 各大 IDE/Agent 宿主已支持——写一个 server，Claude Desktop/Cursor/你的 Agent 三处通用，这是它比"自定义 API"值钱的地方
  • A2A（Agent-to-Agent）：Agent 之间互认与任务委托的协议（Google 牵头）——解决"MCP 连的是工具，Agent 连的是谁"
  • ACP/ANP：其余互操作尝试（ACP 重脑机对接标准、ANP 重去中心化身份），知道名字和分工即可，全部【了】
🔧 动手 8.7（README 指定）①写上面的 notes-search server；②接进 Claude Desktop 或自己的 loop 验证工具真的被调用；③（可选）在 Claude Desktop 里问"帮我搜笔记里提到 chunking 的地方"，观察它调用你的 server。做通后你就有了一件毕业项目 M3 零件：自己的 MCP server。

框架格局（五层）

验收：五层各是什么、什么场景上哪层？实践：读 pi 源码，对照自己的 8.2 写 300 字对比。
💡 钩子写完 8.2 你已经站在 L0（裸写）。框架五层地图帮你定位"什么时候该往上爬一层"——每层的取舍都是同一个：抽象省的时间 vs 黑盒藏掉的控制力。
层代表是什么何时用
L0 裸写你的 8.2while + 注册表，~100 行学习期；需要完全控制（人工审批、自定义循环逻辑）
L1 极简 harnesspi（TS）把 L0 的公共件（循环/工具/消息管理）打包成小库，源码小到能读完想省 boilerplate 又不想黑盒
L2 官方轻量 SDKOpenAI Agents SDK / Claude Agent SDK / Vercel AI SDK 的 Agent厂商出的标准件：handoff、guardrail、session 等原语已在对应生态里、需要标准原语
L3 编排框架LangGraph.js把 Agent 流程建成显式状态图（节点/边/条件），持久化/回放/人工介入一等公民复杂多步流程要可视化、要 checkpoint、要人审节点
L4 整装 harnessDeep Agents自带规划/子 Agent/文件系统的"开箱即用深度 Agent"快速验证深度任务形态
L5 角色化/低代码【了】CrewAI/AutoGen/Dify/Coze角色预设+拖拽编排，面向非程序员demo/非技术同事参与；不满足定制就降回 L2~L3
📝 选层心法从 L0 起步往上爬，唯一的爬层理由是"遇到了这一层专门解决的问题"（要 checkpoint → L3；要多 Agent handoff 原语 → L2）。反方向（从 L5 起步往下砸）是社区最常见的弯路——黑盒里出的问题没读过 L0 的人根本定位不了。你先写 L0 再读源码的路线，恰是爬梯的正确姿势。

8.9

Agent Skills【浅】

了解级：技能包是什么、与 MCP 怎么互补。
  • Skills = 按需加载的指令+脚本包：一个带 SKILL.md（说明+流程）和可选脚本的文件夹，Agent 判断当前任务相关时才把它的指令加载进上下文
  • 与 MCP 互补关系：MCP 管"接工具"（能力从哪来），Skills 管"教方法"（这类任务的最佳流程是什么）——比如"发布版本"技能包 = 一套步骤指引 + 调用已有 git 工具的顺序经验
  • 本质是 5.5 上下文工程的进一步精细化：不是把所有说明书常驻上下文，而是按任务路由——又一个"稳定在前、按需在后"
8.10

状态持久化与断点恢复【浅】

了解级：checkpoint 的本质与最小实现。
  • 本质一句话：Agent 是长时程状态机——把 messages + 工具注册表状态定期快照到盘，崩溃/关闭后从快照续跑。没有它，跑 30 分钟的任务一崩全没
  • 最小实现：每轮循环后 writeFileSync("state.json", JSON.stringify(messages))；重启时读回来接着循环——你 5.4 学的"历史是剧本"在这里的价值时刻：剧本在，戏就能接着演
  • 进阶形态：L3 框架（LangGraph）内置 checkpoint + 时间旅行（回放到任意节点重跑）；毕业项目的"可中断恢复"（8.15）就是用户级 checkpoint
8.11

Computer Use 与浏览器操作【浅】

了解级：屏幕/浏览器当工具的原理与现状。
  • Computer Use：把"截图→模型看图→输出坐标点击/键入"做成工具循环——LLM 直接操作 GUI（Claude 的 computer use 能力、OpenAI 的 Operator）。原理你全懂（视觉输入=4.11 万物皆 token；循环=8.2），新东西只是"屏幕截图"这个工具
  • 浏览器操作：两种路线——DOM 型（Playwright 拿结构化元素列表给模型选，准但只管浏览器）和视觉型（截图点击，通用但脆）。你的 ZCode 环境里的浏览器工具就是 DOM 型
  • 现状判断【浅】：慢、贵、脆（UI 一改就失效），适合"没有 API 只有人肉流程"的兜底场景——有 API 时永远优先 API 工具

Agent 常见失败模式与调试【精】

验收：五大失败模式各长什么样、怎么定位？提示注入实战：构造一次攻击并修一道防线。
💡 钩子Agent 调试和新手前端调试有神似之处：问题从来不在你以为的地方。最大的心智转变：不要盯着"模型蠢不蠢"，盯轨迹——轨迹里每一轮模型都给出了它的理由，坏结果 = 某一环给的信息不够（工具描述、错误回喂、上下文截断）。

五大失败模式（你将在 agent-lab 里亲手撞到）

模式现场定位修法
①工具误选该用 A 工具时选了 B看轨迹里的候选——description 地盘重叠8.3 四要素重写描述，划清边界
②参数幻觉传了不存在的文件名/格式错看 arguments 原文——模型在编参数schema 加枚举/示例；错误回喂给可选项（8.3 正面教材）
③死循环同一个失败调用重复 5+ 次轨迹里同参数连发——错误信息没给"下一步"失败回喂带建议；循环里加"同参调用计数"熔断

⑤过早放弃"我无法完成"但其实工具够用它只试了一次就停错误回喂带重试建议；system 里明确"失败可换法重试"
📝 调试工作流所有模式共用一个入口：打开 8.13 的轨迹日志 → 找到行为拐点的那一轮 → 问"这轮它看到了什么信息？" → 九成答案是没有（描述缺、错误信息烂、或上下文被截掉）→ 改信息而不是改运气。只有一成是真模型能力不足——那时才考虑换模型或拆任务。

8.13

评估与可观测

验收：tracing 记什么？轨迹评测和 7.6 评估的异同？LLM-as-judge 怎么用才不翻车？
💡 钩子7.6 你学过"评估驱动迭代"（20 题+通过率）——但那评的是单点检索；Agent 评的是多步轨迹：同样的任务，今天 6 轮完成、明天 11 轮绕路、后天死循环——没有轨迹记录，你连"它这次干了什么"都不知道，谈何评估。可观测是评估的前置。

Tracing：最小可用版（动手核心）

8.2 的骨架里已经埋了 console.log——升级成结构化记录：

// 每轮追加一条轨迹事件（内存数组，收尾落盘）
const trace: any[] = [];
// 循环内：
trace.push({ t: Date.now() - t0, round, type: "llm_call", messagesBytes: JSON.stringify(messages).length });
trace.push({ t: ..., round, type: "tool_call", name, args, ok, outPreview: out.slice(0, 200) });
// 收尾：
writeFileSync(`logs/trace-${stamp}.json`, JSON.stringify({ task, rounds: trace, finalAnswer, usage }, null, 2));

记录三要素：时间线（每步何时）、决策（模型要了哪个工具）、数据流（bytes/预览）。有这三样，8.12 的五大失败模式全部可定位。进阶才上 OpenTelemetry/专业平台（LangSmith/Langfuse）——概念一致，别急着上重型。

评估栈（从单点到轨迹）

层评什么方法对应旧知识
单点检索RAG 命中Recall@k（7.6 的 20 题）7.6
轨迹评测过程对不对测试任务集 + 断言：调了该调的工具没、轮数预算内没、没碰不该碰的文件本章 tracing
结果评测最终答案对不对人工抽检 / LLM-as-judge 对照评分下面
CI 回归门禁改动没让旧能力退化测试集跑分，低于基线不让合并7.6 的"防退化"思想+代码 CI

LLM-as-judge：好用但有三坑

  • 用强模型当裁判，给评分标准 + 参考答案 + 待评答案，让它按维度打分——规模化评估的主力
  • 坑①：裁判偏袒长答案/自信口吻 → 评分标准里显式反偏（"长度不加分"）
  • 坑②：裁判和被评者同源（同一模型家族）→ 换个家族当裁判
  • 坑③：把裁判分当绝对真理 → 定期人工抽检校准（7.6"种子必须人工"的同一逻辑）

8.14

安全

验收：提示注入的完整防御栈？权限最小化落到代码是什么？人在环加在哪？
💡 钩子8.12 你已经亲手钓过一次鱼、修过一次防线——这节把单点经验升级成防御栈。先立总纲：Agent 的安全模型 = 假设模型会被骗，然后让"被骗"也不致命。不是"防住所有注入"（做不到），是把每次失陷的爆炸半径压到最小。

提示注入：复习+补全

  • 5.6 的机制解释仍然成立：指令与数据同一条 token 通道，无硬边界。8.12 实验后你有了体感：声明式防线（system 里说"别听文件的"）能提高成本、不保证封死
  • 补全：间接注入才是主威胁——恶意指令不在用户输入里，而在 Agent 将要读的资料里（网页/邮件/文件/工具返回值）。你的知识库 RAG（第 7 章）把外部文档喂进上下文时，就是间接注入的入口
  • 防御栈（从便宜到贵）：①输入消毒（剥 HTML 注释/可疑标记）②不可信内容包裹声明 ③权限最小化（真正的中坚，见下） ④高危动作人在环 ⑤输出过滤（模型要执行的动作过白名单）

权限最小化：落到代码的三条

条目反面（常见错）正面
工具白名单Agent 常驻全部工具按任务阶段动态挂载（5.5 老原则的安全版）：整理阶段只挂 read/list
路径/参数白名单read_file 收任意路径path.basename + 目录前缀校验（你 5.4 就写了）
凭证最小权限Agent 拿管理员 OAuth token每个集成单独申请最小 scope；API key 只给必要端点；凭证不进模型上下文（Key 泄漏进 messages = 永久驻留剧本）

人在环与沙箱

  • 人在环的插桩点：循环里工具执行前判断"高危？"→ 暂停、渲染确认弹窗、用户批准才继续（8.15 的交互设计核心件；手写循环的价值时刻——SDK 黑盒里塞不进这个）。判定线：不可逆/外发/花钱三选一即高危（删文件、发邮件、付款）
  • 沙箱：把执行环境关进笼子——文件系统限定目录、网络出站白名单、子进程限时。桌面应用（Electron）天然有进程边界可利用，毕业项目 M6 的安全题就是"Agent 的工具能碰哪些目录"
  • OAuth2/API key 最小权限【浅】：给 Agent 的每个第三方集成单独走 OAuth 流程、scope 按需申请、过期轮换——绝不做"一个大 token 走天下"
🔧 动手 8.14（随 8.12 延伸）给 agent-lab 落三条防御并各写一行测试：①工具动态挂载（整理任务不挂 write）；②write_file 白名单（8.12 已做的话补一个绕过尝试）；③write 前人工确认（CLI 里 y/n）。全部通过后，把"防线清单"写进本章笔记——毕业项目安全设计的第一稿。

验收：四件交互（计划预览/进度可视化/可中断恢复/确认弹窗）各自解决什么信任问题？毕业项目 M6 零件。

自检

全过 + 四件产出 → 勾掉 8.1–8.15 与本章产出。这是全路线最重要的一章。
Q1（8.1）Workflow vs Agent 的判定线？为什么多数场景该用工作流？
控制流谁决定：代码编排=工作流，模型自主=Agent。Agent 的自由度用可靠性换——路径漂移、成本不可预算。结构固定的任务用工作流（可预测可预算），只有开放任务（修 bug/调研）才值得 Agent。
Q2（8.2）Agent Loop 五大件？两个终止条件分别谁决定？
工具注册表、LLM 调用、终止条件、历史管理、并行执行（Promise.all 按 id 回喂）。语义停=模型决定（不再发 tool_calls）；硬停=代码决定（maxRounds 保险丝）。
Q3（8.3）工具 description 四要素？错误信息的正面写法？
做什么/边界（防误用）/何时用/不用于何（划地盘）。错误信息=发生了什么+为什么+模型该怎么改——给模型的修正提示，不是程序员堆栈。
Q4（8.4）先规划 vs 边走边看的取舍？混合正解？
规划：长任务不迷路、计划可审批，但可能基于错误假设；边走：零成本快，但长任务漂移。正解=按复杂度混用：简单直接 ReAct，复杂先出计划（给用户确认）→执行→允许重规划。
Q5（8.5）短期记忆三策略？长期记忆的毕业项目取舍？
窗口截断（便宜会忘，补救=目标常驻 system）、工具结果剪枝（性价比王）、摘要压缩（compaction）。长期：结构化卡片起步（偏好/路径/状态），向量记忆=第 7 章复用。
Q6（8.6）三种多 Agent 模式？不该拆的判断？
编排者-工作者（拆发汇总，Deep Research 型）、Handoff（接力转交）、子 Agent（上下文过滤器）。不该拆：单循环 10 轮内能干完/动机是排场；该拆：子任务上下文天然隔离/单 Agent 上下文爆了。
Q7（8.7）MCP 三角色？为什么说"协议换了，循环不改"？
Server（暴露工具）/Client（连接转发）/宿主（挂进注册表）。MCP 工具清单≈toolsForApi、工具调用≈execute()——只是工具来源从"自己写"变"拉协议"，8.2 的 while 一行不改。
Q8（8.8）五层各代表？爬层唯一正当理由？
L0 裸写（你的 8.2）→L1 极简（pi）→L2 官方 SDK（handoff/guardrail 原语）→L3 编排（LangGraph，checkpoint/人审）→L4 整装（Deep Agents）→L5 低代码。爬层理由：遇到了该层专门解决的问题（要 checkpoint→L3），而非"听说厉害"。
Q9（8.12）五大失败模式？共同的调试入口？
工具误选/参数幻觉/死循环/目标漂移/过早放弃。共同入口：开轨迹→找行为拐点轮→问"这轮它看到了什么信息"→九成是信息不够（描述缺/错误烂/上下文截）→改信息不碰运气。
Q10（8.13）tracing 最小三要素？LLM-as-judge 三坑？
时间线+决策（要了哪个工具）+数据流（bytes/预览）。坑：偏袒长答案（标准里反偏）、裁判同源（换家族）、当绝对真理（人工定期校准——7.6 种子人工的同一逻辑）。
Q11（8.14）Agent 安全总纲？权限最小化三条？人在环的判定线？
总纲=假设模型会被骗，让被骗不致命（压爆炸半径）而非防住所有注入。三条：工具按阶段动态挂载、路径/参数白名单、凭证最小 scope 且不进上下文。高危判定线：不可逆/外发/花钱 三选一。
Q12（8.15）四件交互各回答什么焦虑？为什么它们依赖手写循环？
计划预览（要干嘛？）/进度可视化（卡死没？）/可中断恢复（能停能续吗？）/确认弹窗（会乱来吗？）。全部需要在循环里插桩（执行前暂停、事件外发）——SDK 黑盒循环插不进，手写 loop 是它们的地基。
