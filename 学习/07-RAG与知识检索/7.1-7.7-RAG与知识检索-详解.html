7.1

为什么需要 RAG

验收：RAG 同时解决的三个问题各是什么？和微调的边界？和"直接塞全文"的边界？
💡 钩子先造一个失败现场：问 chat-app"我的笔记里关于 MCP 都记了什么"——模型必然开始幻觉编造，因为它根本没读过你的仓库。模型的知识 = 训练数据冻结的快照（4.4 知识截止），你的笔记不在里面，永远不在。RAG 就是不重新训练、让模型"开卷考试"的工程方案。

三个问题，一个方案

问题机制根源RAG 怎么解
知识截止训练数据冻结在某时刻（4.4/4.8），新事实不在参数里检索时把最新的资料喂进上下文
私有知识你的笔记/文档/代码从来不在任何公开语料里检索你的资料喂进上下文
幻觉概率续写器，缺依据时照样生成（4.8）答案被要求只基于检索到的内容——有据可查，且有出处（7.7）

RAG 一句话定义与全流程图

RAG（Retrieval-Augmented Generation）= 先检索、后生成：把和问题相关的资料片段找出来，塞进 prompt，让模型"照着资料答"——本质是 5.5 上下文工程的一个垂直应用（"检索内容"那一行的完整工程化）。

两阶段：离线把知识切块向量化存库（一次）；在线把问题向量化、捞最近邻、塞进 prompt 开卷考（每次）

边界一：RAG vs 微调（什么时候用哪个）

RAG微调（第 9 章）
本质给模型看资料（上下文注入）改模型的脑（改权重）
适合事实性知识、频繁更新、要出处风格/格式/行为模式，相对稳定
更新成本加文档即生效（重新索引几分钟）重训练一次（钱+天）
幻觉抑制强（有据可引）弱（还是会编）
口诀"知识"用 RAG"行为"用微调
📝 指路牌这张表只是立边界——微调本体（LoRA 是什么、什么场景真值得微调、和 RAG 组合使用）在大纲 第 9.1 节正式讲（【浅】章，概念到直觉为止）。读到这里只需记住分工口诀：知识更新频繁、要出处 → RAG；风格/格式/行为模式稳定不变 → 才考虑微调。你的毕业项目（知识库+Agent）大概率全程用不到微调——别提前焦虑。

边界二：RAG vs 直接塞全文（长上下文不能白嫖吗）

窗口 128K+ 的时代，小文档库直接全文塞进 prompt 当然行（你的笔记仓库全文可能不到 100K token）。但 RAG 仍然赢在：① 成本——每轮全量重发 vs 只发 Top-5 片段（缓存也救不了每次都不同的尾部）；② 精度——lost in the middle（5.5）：塞 50 页找一页，中间的会被漏读；③ 规模——100 万字的时候物理上就塞不下了。经验线：几百字~几千字直接塞；几万字以上 RAG。

🔧 动手 7.1（10 分钟）失败现场确认：在 chat-app 里问"我的 5.3 实验台的四个档位分别是什么？"——观察模型是（a）坦承不知道（运气好），还是（b）一本正经地编造细节。截图/记录这个回答，7.6 做完知识库后用同一问题再问一次——两相对照就是你的第一个 RAG 评估数据点。
7.2

文档解析与 Chunking

验收：为什么"切法直接决定质量"？三种切法各自的问题？切块该多大、为什么留重叠？
💡 钩子RAG 系统的质量上限，在 embedding 模型还没跑之前就被 chunking 决定了一大半。切烂了（一句话被拦腰斩断、一个问题散在两块里），后面再先进的检索也救不回来——垃圾进垃圾出，这是 RAG 的第一定律。

解析：先把"垃圾"挡在门外

md/html/pdf 各有坑：md 相对干净（你的仓库主力）；html 要剥脚本/导航/广告；pdf 最险（双栏排版、扫描件、表格错位）。策略：从自己吃得了的开始——本章大作业只做 学习/ 和 资源/ 的 md，解析这一步几乎零成本；pdf 支持留到需要时再上（mammoth/docx4js/pdf-parse 类库）。

Chunking：三种切法

① 固定长度切（最简单）

  • 每 500 字符切一刀
  • 问题：语义拦腰斩——"MCP 是协议"和"用来连工具"分家
  • 只适合：无明显结构、快速原型

② 按结构切（md 的天选切法）✓

  • 按标题层级切：## 一节 = 一块
  • 天然语义完整——作者已经替你切好了
  • 超长小节再降级内切（二级结构+固定长度兜底）

③ 语义切（embedding 感知）

  • 相邻句向量相似度骤降处 = 话题转折 = 切点
  • 效果最好、成本最高（要先跑一遍 embedding）
  • 本章不需要——你的笔记结构极好

三个关键参数（手搓知识库你会逐个摸到）

参数经验值（中文 md）为什么
块大小300~800 字符太小→语义碎（一块说不清一件事）；太大→检索精度稀释（一块混多件事，向量"平均化"，问 A 找到的是 AB 混块）
重叠 overlap10~20%（如 500 字块叠 80 字）防"答案恰在切缝上"——两块都含缝边内容，总有一块完整
元数据每块带：文件路径、标题、行号不只是检索用——7.7 引用溯源全靠它（"出处：学习/08-…/README.md 第 12 行"）
📝 给你自己仓库的特调你的 md 有天然优势：标题结构规整、每节主题单一、还有"本章笔记"这类自描述段落。按结构切（## 级）+ 超长节内切就是最优解，连 overlap 都可以小。另外每个块建议在向量化前拼上"文件路径+标题"前缀（如"【学习/05-…/README.md · 本章笔记】正文…"）——让这块的向量携带"我来自哪"的语义，检索和溯源双双受益。这招就是 Anthropic《Contextual Retrieval》的核心思想（README 进阶选读）的丐版。
🔧 动手 7.2（纸面推演，15 分钟）拿 学习/05-Prompt与上下文工程/README.md 手动演练：①如果你按固定 300 字切，哪些概念会被拦腰斩断（找出 2 个具体例子）？②按 ## 结构切会得到几块、每块多大？③"5.4 Function Calling"那节如果超 800 字，你打算怎么二级切？把答案写进笔记——这三个问题的答案就是将来 chunking.ts 的伪代码。
7.3

Embedding 模型与向量库

验收：向量库解决什么（对比数组暴力搜）？为什么查询和文档必须用同一个模型？桌面场景为什么选 LanceDB？
💡 钩子4.2 你亲手算过余弦相似度——但那是 5 个句子两两算。如果库里有一万块，每个查询算一万次余弦呢？向量库 = 当数据多到暴力搜开始变慢/变贵时的专业替代。本节的工程路线就是大纲写的：内存数组起步理解原理 → LanceDB 上生产。

Embedding 模型：检索的标尺必须统一

  • 选型只看三样：语言（中文主力选 BAAI/bge-m3、Qwen embedding 系；多语言 bge-m3 最稳）、维度（1024/1536，存储存储成本）、排行榜（MTEB/C-MTEB 当期排名参考即可，你的数据实测才算数）
  • 铁律：索引和查询必须用同一个模型。不同模型的向量不在同一个"语义空间"——4.2 讲过每个模型有自己的一套坐标系，跨模型算余弦 = 用北京的地图坐标在上海导航，结果纯随机。换模型 = 全库重新索引。
  • 厂商现实：DeepSeek 没有 embedding API（4.2 就发现过）——需要另配：硅基流动（BAAI/bge-m3，便宜）、智谱（embedding-3）、OpenAI（text-embedding-3-small）。都是一个 HTTP 调用：文本进、向量出。
  • 文件名不是内容名：图片（multimodal embedding）、代码（按符号切）有专门模型——本章 md 场景用文本模型即可。

向量库：从数组到 LanceDB

阶段做法瓶颈定位
内存数组所有块向量载入数组，查询时逐个算余弦排序O(N)：1 万块×1024 维≈每个查询 1000 万次乘加——慢但还能忍；10 万块就不行了学习期必做——原理一目了然（本质上就是 4.2 那几行代码的规模化）
LanceDB嵌入式向量库：一个本地目录就是库，零部署零服务进程，TS 原生近似最近邻（ANN）索引，查询近 O(1)桌面应用的标配选择（大纲钦点）：数据在本地文件里、不联网、和你 Electron 毕业项目气质完全吻合
云端托管Pinecone / 阿里云向量检索等要联网、要钱、数据出境问题多人/大规模服务才需要——你的场景用不上

LanceDB 五分钟体感（真实代码）

import * as lancedb from "@lancedb/lancedb";
import("@lancedb/lancedb").connect("学习知识库.lance")  // 目录即数据库

    const tbl = await db.createTable("chunks", [{  // 首次建表：向量+原文+元数据一行一条

7.4

检索策略：相似度 / 混合 / 重排

验收：纯向量检索的三类失败？混合检索为什么是标配？rerank 解决什么、代价是什么？
💡 钩子向量检索不是银弹——它有三种标志性翻车，每一种你将来都会撞上。检索策略 = 知道翻车姿势 + 花小钱补救。

纯向量检索的三类翻车

翻车场景根因
专有名词失明搜"stepCountIs"——相关笔记排不进 Top-5embedding 对生僻符号/API 名的语义把握弱，不如关键词匹配直接命中
语义漂移问"MCP 怎么配"，捞回来一堆"配置文件格式"泛泛之谈相似≠相关：向量距离近只说明"话题相邻"，不保证"能回答"
大库稀释库到几十万块，Top-5 越来越"差不多"ANN 近似的精度损失 + 高频话题块霸榜

三层策略，逐层加钱加精度

① 纯向量（基线）

  • 查询向量 → 余弦 Top-K
  • 零额外成本，先跑通它
  • 你的小库（几千块）纯向量往往已经够用

② 混合检索（标配）

  • 向量 Top-K + BM25 关键词 Top-K，结果融合（RRF）
  • 专有名词由关键词救，语义问题由向量救——互补
  • LanceDB 支持全文索引，混合查询一行

③ 重排 rerank（精修）

  • 召回 50 块 → rerank 模型逐对"问题-块"打精分 → 取 Top-5
  • 解决"相似但不回答"的漂移——rerank 是问答相关性专用模型
  • 代价：多一次 API 调用+延迟；查询改写/多路召回/GraphRAG 见 7.5

RAG 发烧友的"三层楼"，你的知识库该住几楼

一楼（纯向量）先住下，用 7.6 的评测集体检：通过率 ≥80% 就不搬家；<80% 再看失败案例属于哪类翻车——专有名词翻车上混合检索，语义漂移上 rerank。评估驱动升级，不要一上来就盖三层楼——那是 RAG 教程最常教的过度工程。你自己的库大概率一楼+二楼就到顶了。

7.5

进阶形态【浅】

了解级：每个一句话，知道名词对得上人即可。
形态一句话什么时候你会需要
查询改写用 LLM 把口语问题改写成检索友好形式（"那个工具协议咋配来着"→"MCP 配置方法"）；含多查询扩展（一个问题拆成 3 个角度各查一遍）用户输入口语化严重时
多路召回同一问题同时查向量/BM25/摘要索引等多路，合并精排——7.4 混合检索的泛化版单一索引明显不够时
GraphRAG从文档抽实体关系建知识图谱，检索沿图走（"MCP 的作者还写过什么"需要跨文档跳转）知识之间关系密集、多跳问题时——你的笔记库暂不需要
多模态 RAG图表/截图也切块向量化（用多模态 embedding），问"那张架构图"能命中文档含大量图时
Contextual RetrievalAnthropic 方案：每块入库前用 LLM 生成"这块在全文中的位置说明"拼接后再向量化——解决切块后断章取义通用 RAG 精度瓶颈时；你用"路径+标题前缀"丐版即可

学习姿势：这五个名词知道"解决什么问题"即可，全部【浅】。真正的进阶信号是 7.6 的评测集告诉你"基线不够用了"——到时候再回来按需取用。

7.6

RAG 评估：Recall@k / 忠实度 / 引用准确率

验收：三个指标各量什么？"评估驱动迭代"的操作闭环是什么？动手：20 题评测集。
💡 钩子RAG 最贵的坑：凭感觉调参。换 chunking、加 rerank、改 Top-K——每次都"感觉好了点"，没有一个数字告诉你到底好没好。README 指定的动手（手写 20 题评测集）就是把你从"感觉派"扳成"数字派"——这也是 8.13 评估思想的第一次落地。

三个指标，各量一段管道

指标量什么怎么算（丐版）低分说明
Recall@k检索段：该找到的块，Top-k 里找到了吗20 题里"期望命中的块进了 Top-k"的比例chunking 或 embedding 或检索参数有问题——改这里，别动 prompt
忠实度 (faithfulness)生成段：答案是否忠于检索到的内容答案里的关键论断能在上下文里找到支撑吗（LLM-as-judge 或人工）模型在自由发挥——加强"只基于资料答"的 system 约束
引用准确率溯源段（7.7）：给出的出处指对了吗抽查引用的文件/行号，点开验证元数据链路断了——检查块的元数据是否随路携带

诊断顺序很重要：先 Recall@k，再忠实度，最后引用——检索是上游，上游坏了改下游（prompt/引用格式）全是无用功。

评估驱动迭代的闭环

写 20 题（问题 + 期望命中的块） → 跑基线 → 通过率数字
   → <80%：看失败案例 → 判断断在哪段（检索/生成/引用）
   → 改对应段 → 重跑 → 数字变了吗？
   → ≥80%：收工。以后每次改动（换 embedding/加 rerank）重跑一遍防退化

这套"先有量尺再动手术"的思想直接迁移到第 8 章 Agent 评估（8.13）——RAG 评估是你 evaluation-driven 开发的第一课。

7.7

引用溯源【精】：答案带出处、可跳原文

验收：溯源链路怎么搭？引用在 UI 上怎么呈现？为什么说这是知识库应用的刚需而非装饰？
💡 钩子ChatGPT 的引用是网页链接，你的知识库引用是自己的笔记——"这个说法来自 5.3 详解的三层方案表"，点开跳到原文。没有溯源的知识库 = 不可审计的黑盒：用户没法验证答案、错了没法定位、你自己没法调试。7.6 的"引用准确率"量的就是这条链路。

溯源链路：元数据的一路携带

溯源 = 元数据从入库到 UI 的全链路携带；断任何一环，引用就是装饰品

生成端：让模型引用（system 模板）

你是知识库助手。只基于下面的资料回答；资料不足时明确说"资料里没有"。
资料（每段开头标了来源编号）：
[1]（来源：学习/05-…/README.md · 本章笔记 · 行 22）正文……
[2]（来源：知识大纲.md · 8.7 行）正文……

回答要求：
- 每个论断后标注来源编号，如 "…… [1]"
- 综合多个来源时逐个标注 [1][2]
- 资料之间冲突时，指出冲突而不是擅自合并
这套格式约束就是 5.2 的正向指令原则：不说"要有引用"这种弱指令，而是给可断言的格式（"论断后标编号"）——7.6 的引用准确率才有得算。

展示端：前端怎么呈现（毕业项目里的样子）

  • 行内标号：答案里的 [1] 渲染成小徽章（chat-app 的 parts 里加一个 citation 部件类型）
  • 底部来源卡：答案下方列出全部引用——文件名 + 标题 + 行号，点击行为分两档：md 文件直接打开定位行号（桌面应用天然优势：Electron 打开本地文件+滚动到行）；网页版则显示路径文本
  • 交互细节：hover 标号预览原文片段（元数据里把块原文也带上就行）
📝 为什么是刚需不是装饰三个工程理由：①可验证——用户敢信答案（特别是"我该按哪个步骤配 MCP"这种执行类回答）；②可调试——你看到错误引用立刻知道是检索段坏了还是生成段坏了（7.6 诊断链）；③可迭代——引用准确率是回归测试的免费指标。第 8 章 Agent 的"工具结果也要引用"（8.13 可观测）是同一思想放大。
🔧 动手 7.7（随大作业做）在知识库答案里检查三件事：①每个论断都有标号吗（忠实度+引用联动）；②点开一个引用，跳到的位置和论断对得上吗；③问一个"资料里没有"的问题（如"我的密码是什么"）——模型应该拒答而不是编。三条全过，溯源链路才算通。

Q1（7.1）RAG 同时解决的三个问题？和微调的分工口诀？
知识截止（检索最新资料）、私有知识（检索你的资料）、幻觉（有据可查+可引用）。口诀："知识"用 RAG，"行为"用微调——RAG 是开卷考（上下文注入），微调是改脑子（改权重），更新成本天差地别。
Q2（7.1）128K 窗口时代为什么还要 RAG？经验线？
成本（每轮全量重发 vs Top-5 片段）、精度（lost in the middle：塞 50 页找一页中间的漏读）、规模（百万字塞不下）。经验线：几千字直接塞，几万字以上 RAG。
Q3（7.2）为什么说 chunking 决定质量上限？三参数经验值？
切烂了语义就碎了，后面再强的检索也救不回（垃圾进垃圾出）。块大小 300~800 字符（碎→说不清，大→向量平均化）、重叠 10~20%（防答案在切缝上）、元数据（source/heading/line——7.7 溯源全靠它）。
Q4（7.3）为什么索引和查询必须同一个 embedding 模型？
不同模型的向量在不同语义空间——坐标系都不同，跨模型余弦结果纯随机。换模型=全库重新索引。
Q5（7.3）数组暴力搜和 LanceDB 的分水岭？桌面为什么选 LanceDB？
数组 O(N) 逐个余弦，万块勉强、十万块不行；LanceDB 用 ANN 索引近 O(1)。桌面选它：嵌入式（零部署）、本地（隐私）、TS 一手——和 Electron 毕业项目气质吻合。
Q6（7.4）纯向量检索三类翻车？混合检索救哪类？
专有名词失明（embedding 对生僻 API 名弱）、语义漂移（相似≠能回答）、大库稀释。混合检索（向量+BM25+RRF）救专有名词类；rerank（问答相关性精排）救漂移类。
Q7（7.6）三指标各量哪段管道？诊断顺序？
Recall@k 量检索段、忠实度量生成段、引用准确率量溯源段。顺序：先 Recall@k——检索是上游，上游坏了改 prompt 全是无用功。
Q8（7.6）"评估驱动迭代"的闭环是什么？
20 题（问题+期望命中块）→ 跑基线得数字 → <80% 看失败案例定位断段 → 改那段 → 重跑看数字 → ≥80% 收工；此后每次改动重跑防退化。先有量尺再动手术——8.13 的第一课。
Q9（7.7）溯源链路四段是什么？断一环会怎样？
入库带元数据（source/heading/line）→ 检索连元数据一起取 → prompt 编号[1][2]要求标注 → 前端渲染可点卡片跳原文。断任何一环，引用就从"可审计证据"退化成"装饰品"。
Q10（7.7）为什么溯源是知识库的刚需而非装饰？
可验证（用户敢信执行类回答）、可调试（错误引用立刻定位坏在哪段）、可迭代（引用准确率=免费回归指标）。第 8 章"工具结果可观测"是同一思想放大。
