6.1

API 接口规范与 SDK

验收：错误码四大家族各代表什么？"换模型只改 base_url 和 key"的边界在哪？SDK 封装的和没封装的是什么？
💡 钩子这一节 80% 是复习：messages / usage / tool_calls / finish_reason / SSE 你全在 first-call 里见过真身。新东西只有一样：错误码的系统观——以及一个重要的认知：HTTP 协议和 SDK 是两层东西，SDK 不改变协议，只是替你说了你想说的话。

家族典型码含义你的应对

📝 判断口诀4 字头除了 429 都不该重试（你的错，重试还是错）；429 和 5 字头才值得重试（世界的错，等等会好）。错误体里的 JSON（如 DeepSeek 的 error.message）通常直接说了人话——你 5.4 里见过 messages[0].content: invalid unicode 这种，读它比猜快。

"换模型只改 base_url 和 key"的边界

OpenAI 兼容协议让你在 DeepSeek / 智谱 / 硅基流动 / OpenRouter 之间迁移几乎零成本——但兼容的是协议形状，不是全部能力。踩过的和将踩的边界：

  • ✅ 真零成本：chat/completions 主干、messages/temperature/max_tokens/usage
  • ⚠️ 名同实异：json_schema 支持度、reasoning 参数名（reasoning_effort / thinking / enable_thinking 各家不同）、多模态字段
  • ❌ 不兼容：embedding 模型名、专用端点（如 DeepSeek 的 FIM 补全）、各家独有参数

你亲历过的实例：请求 deepseek-chat 返回 model:deepseek-flash（服务端静默映射）——兼容协议下"模型名"只是个请求字符串，响应里的 model 才是真相。跨厂商迁移时，上线前先跑一遍你的核心用例做冒烟测试。

SDK 是什么，不是什么

SDK（openai 官方包、各家 SDK、Vercel AI SDK）= 替你处理 HTTP 细节和类型的客户端库：拼请求、流式解析、错误归类、TS 类型。它不改变协议——你在 first-call 手搓的每个字节它都在帮你拼，只是你看不见了。什么时候值得上 SDK：写正式应用（第 6 章开始，永远）。什么时候裸 fetch 更好：学习协议（你已完成）、排查问题（剥掉中间层看真相）。

🔧 动手 6.1（轻量，15 分钟）错误码冒烟测试——故意制造三种错误，在控制台或 curl 里看错误体的样子：
  1. 401：Authorization 换成 Bearer sk-wrong → 读错误体里的提示
  2. 400：response_format: {type:"json_object"} 但 prompt 里不含"JSON"字样 → 印证 5.3 的坑
  3. 404：model 写成 deepseek-nonexist → 看模型名错误长什么样
观察：哪些错误体给了人话？哪些只有干巴巴的码？把你下次排查时会先看的字段记进笔记。
6.2

流式输出与前端 UX

验收：流式的 UX 价值有数据支撑吗？前端渲染流式的三个工程问题是什么？流式下怎么拿结构化数据？
💡 钩子流式的原理你全懂了（SSE 信封、到货即完整的小 JSON、ndjson 翻译）——这节讲你还没碰过的那半：拿到 delta 之后，前端怎么把它变成好的体验。这是 2.3 埋的"为什么 EventSource 不够用"的正式回收。

流式的 UX 价值：先说数字

流式不减少总耗时（同样的 token，同样的生成速度）——它改变的是首字时间 TTFT（Time To First Token）：非流式要等全部生成完（长回答 10~30 秒），流式 1~2 秒内见到第一个字。感知心理学：用户对着"空白页等 20 秒"会走，对着"逐字打出来的答案"愿意等完——可感知进度就是一切。另一个硬好处：长回答可以边生成边读，用户可能在第 3 秒就得到答案，直接打断后续生成（省 token 也省时间）。

前端渲染流式的三个工程问题

① 怎么收：EventSource 够吗

  • 原生 EventSource 只支持 GET——LLM 请求是 POST 大 body，不够
  • 方案：fetch + ReadableStream 手拆（你在 first-call 干过）；或 @microsoft/fetch-event-source 库（支持 POST/自定义头/自动重连）

② 怎么显示：增量拼接与 Markdown

  • delta 逐个 append 到 state（React 里注意别每 delta 一次 setState 重渲染全树——用 ref 攒批，requestAnimationFrame 合并刷新）
  • Markdown 半截渲染闪烁：收到一半的 ```代码块、没闭合的表格会渲染成乱apa——对策：节流重渲染（每 100ms 一次）+ 渲染前"补全"未闭合标记
  • 光标跟随：尾部加 ▍ 光标，完成后移除

③ 怎么停：中断与恢复

  • 用户点"停止"→ AbortController.abort() 取消 fetch——上游 SSE 断开，已生成的 token 保留（计费已产生）
  • 断线恢复：SSE 的 id: 行 + Last-Event-ID 头（你在 6.1 的 SSE 标准里见过）——但 LLM API 一般不支持续传，断了就重发

流式下怎么拿结构化数据（5.3 的流式续篇）

结构化输出 + 流式 = 一个新问题：JSON.parse 要等完整文档，而流式的意义就是不等。三个解法，按需选用：

解法做法适用
不用流式结构化输出直接非流式（反正程序消费，TTFT 无意义）多数情况——机器吃 JSON 不需要打字机效果
流式 + 尾端 parse流式收完在 done 时一次性 parse（用户看到 JSON 逐字出现）调试/透明化场景（你的实验台就是这个）
部分 JSON 解析partial-json 类库：解析"到目前为止合法的前缀"，边流边出部分对象前端要展示渐进填充的结构（表格逐行出现）

关键认知：流式的价值在人看；程序吃的输出（Agent 决策、提取器）默认非流式——省掉整个 SSE 层的复杂度。你的 Agent 桌面应用里，唯一值得流式的是聊天窗口本身。

🔧 动手 6.2在 first-call 控制台里做一次"中断实验"：发起一个长回答的流式请求，生成到一半点浏览器停止按钮（或关页面）→ 观察 server.ts 日志里收到多少 chunk 后断开 → 回答两个问题：①已生成的 token 计费了吗（对照 usage，若没收到 usage 块说明上游也断了）？②再次请求时，历史里该放这条残缺回答吗？（提示：assistant 半截话进历史，模型会接着它的语气续——有时正是你想要的，有时是坑。）
6.3

Vercel AI SDK —— 本章主战场

验收：streamText/generateObject/tool/useChat 各替你抽象了什么（对照你手搓过的代码）？动手：聊天 Web 应用跑起来。
💡 钩子AI SDK 是 TS 生态事实标准的 LLM 前端/全栈库。学它的正确姿势不是读文档从头到尾，而是逐个对照你手搓过的代码——每个 API 都回答同一个问题："这个替我干了哪段我写过的苦活？"

四大件对照表（你的手搓 → SDK 的一行）

你手搓过（first-call）苦活AI SDK 的替代还剩给你做的
fetch + Authorization + body 拼装 + res.json()HTTP 细节、类型generateText({ model, messages })选模型、写 prompt
getReader + split("\n\n") + 剥 "data: " + 逐块 JSON.parse + delta 拼接SSE 全套const { textStream } = await streamText(...); for await (const delta of textStream)拿到 delta 后的 UI
tools 说明书 + 四步 for 循环 + JSON.parse(arguments) + role:"tool" 回喂 + MAX_ROUNDSAgent Loop 骨架maxSteps 一行：generateText({ tools, maxSteps: 5 })——SDK 在内部跑完整循环工具的执行函数（execute）
Zod schema + response_format + safeParse + self-heal 重试结构化输出三层generateObject({ schema: MeetingSchema })——Zod 自动转 JSON Schema、自动重试写 schema（你已会）
（还没有）React 聊天组件输入框/消息列表/流式渲染/停止按钮useChat() hook样式与交互定制

看清楚一件事：SDK 抽掉的全是"协议搬运"苦活，没抽掉的是"决策"——选什么模型、schema 怎么设计、工具给哪些、失败怎么办。第 5 章教的就是这些没被抽掉的东西。

核心 API 速写（真实代码，注释标出对应你写过的哪段）

import { generateText, streamText, generateObject, tool } from "ai";
import { createOpenAI } from "@ai-sdk/openai";
import { z } from "zod";

const deepseek = createOpenAI({
  baseURL: "https://api.deepseek.com/v1",  // ← 就是你的 LLM_BASE_URL（注意有的厂商要 /v1）
  apiKey: process.env.LLM_API_KEY,
});

// ① 非流式 = 你 first-call.ts 的 main 干的事
const { text, usage, finishReason } = await generateText({
  model: deepseek("deepseek-chat"),
  system: "你是助手",                        // ← 5.1：system 是你的代码注入的
  prompt: "你好",
});

// ② 流式 = 你 server.ts SSE 翻译器干的事，现在一个 for-await
const { textStream } = await streamText({ model: deepseek("deepseek-chat"), prompt: "讲个故事" });
for await (const delta of textStream) process.stdout.write(delta);

// ③ 结构化 = 你 meeting-notes.ts 的 tidy() 干的事（含自动重试）
const { object } = await generateObject({
  model: deepseek("deepseek-chat"),
  schema: z.object({ title: z.string(), items: z.array(z.object({ owner: z.string() })) }),
  //   ↑ Zod 直接传！SDK 自动转 JSON Schema 给模型（5.3 的"两份 schema 手写两遍"问题被消灭）
  prompt: "整理这份笔记：…",
});
object.items[0].owner; // 类型安全，无需 safeParse（SDK 保证）

// ④ 工具循环 = 你 5.4 实验台的 runAgent() 干的事
const result = await generateText({
  model: deepseek("deepseek-chat"),
  prompt: "帮我看看 todo.md",
  tools: {
    read_file: tool({
      description: "读取 data/ 目录下的文本文件",          // ← 5.4 的说明书
      parameters: z.object({ filename: z.string() }),      // ← Zod 代替手写 JSON Schema
      execute: async ({ filename }) => {                   // ← 5.4 的 execReadFile（白名单在这里！）
        return readFileSync(path.join("data", path.basename(filename)), "utf8");
      },
    }),
  },
  maxSteps: 5,   // ← 5.4 的 MAX_ROUNDS 保险丝：SDK 内部跑 5.4 的整个 for 循环
});

useChat：前端聊天组件的最后一公里

useChat（React hook）把聊天 UI 的状态机全包了：messages（自动维护的历史=你的剧本）、sendMessage、stop（=你的 AbortController）、status（streaming/ready）、data。配 AI SDK 的服务端路由（Next.js App Router 里 toUIMessageStreamResponse()），一个能用的聊天界面 50 行以内。你手搓过的每个环节都能在它的源码里找到对应物——现在读它的文档你会有"哦这就是我干过的那个"的熟悉感。

📝 版本提醒AI SDK 迭代快，API 名会变（v4→v5 改过 useChat 的消息结构、generateText 的返回字段）。本文快照 2026-11，动手时以 ai-sdk.dev 当前文档为准——但抽象层级和四大件的概念结构是稳定的，API 名变化不影响你已理解的心智模型。
🔧 动手 6.3（README 指定 · 本章主产出）聊天 Web 应用：Next.js + AI SDK，流式 + 工具。这是毕业项目 M1 的地基，做慢点没关系，做扎实：
  1. 脚手架：npx create-next-app@latest chat-app --typescript --app → npm i ai @ai-sdk/openai zod；工程放 实验/chat-app/（长期项目待遇，和 first-call 平级）
  2. 服务端路由：app/api/chat/route.ts——用 streamText + toUIMessageStreamResponse()；模型用 createOpenAI 指向你的 DeepSeek 配置（沿用 .env 的思路，Key 走 process.env，只在服务端，永不进浏览器——你 5.3 学到的原则）
  3. 前端页面：useChat + 消息列表 + 输入框 + 停止按钮，先别管样式，能流式打字就行
  4. 加一个工具：把 5.4 的 read_file（白名单 data/）搬进 route.ts 的 tools + maxSteps: 5——你的聊天应用立刻能读文件
  5. 验收三连：流式逐字出现 ✓ / 停止按钮立刻中断 ✓ / "帮我看看 todo.md"能触发工具并总结 ✓

6.4

应用形态：聊天 / 副驾 / 工作流嵌入

验收：三种形态的本质区别？毕业项目属于哪种（这决定你后面章节的取舍）？
💡 钩子"做个 AI 应用"太粗了——形态决定架构：消息流是谁的、上下文从哪来、失败怎么兜底。选错形态，后面全歪。
形态交互模型上下文构成典型例子核心难点
聊天 Chat人发消息→模型回→多轮往复对话历史为主ChatGPT、客服机器人长对话管理（5.5 压缩三板斧）
副驾 Copilot嵌入工作流，人在环边用户正在操作的上下文（当前文件/选中段落/页面）+ 少量对话GitHub Copilot、光标处补全、Notion AI上下文采集与注入（把"你在干嘛"翻译给模型）
工作流嵌入 Workflow程序调用模型，人只在端点任务专属构造（模板+检索+工具）简历解析器、内容审核管道、Agent 的中间步骤结构化输出与可靠性（5.3/6.7）

毕业项目是哪种？—— 三种都是，分层看

你的 Agent 桌面应用不是一个形态，是三层形态的叠加：

  • 外壳是聊天：用户和 Agent 对话（6.3 的聊天应用直接升级）
  • 内核是工作流嵌入：Agent 每一轮内部——模型决策（结构化输出）、工具执行、失败重试——全是程序↔模型的机器对话，用户看不见（5.4/6.3 的 tools + maxSteps）
  • 增强靠副驾：感知用户当前在桌面干什么（活动窗口、剪贴板、打开的文件）注入上下文——这是副驾形态的"上下文采集"，Electron 能做而网页做不了的事

对本章的指导意义：6.3 的聊天应用 = 外壳先行；但 route.ts 里已经放 tool + maxSteps——内核的种子从第一天就种进去。不要做成"纯聊天然后重构"，要做成"聊天壳里长着 Agent 的心脏"。

6.5

成本与延迟工程

验收：prompt caching 的省法与条件？模型路由按什么分流？上下文瘦身从哪几刀下手？
💡 钩子上线前成本是"哦价格表看看"，上线后是"每天账单盯着你"。三个杠杆，每个都你已经有体感基础。

杠杆一：Prompt Caching（你亲眼见过 cached_tokens）

  • 机制：前缀逐字节相同的请求，命中缓存的部分按 1/10 左右计费（各家不同）+ 显著降低 TTFT（不用重新算 KV）
  • 条件苛刻：从头开始逐 token 相同才命中——system 固定、tools 固定、few-shot 固定，放前面不动；任何"今天日期""当前状态"混进前缀，缓存全灭（5.5 的排列黄金法则的成本学版本）
  • 你的数据：4.7 实验里你观察过第二次请求 cached_tokens 的跳变——那就是这个机制
  • DeepSeek 还有硬盘缓存（自动、无标记）；OpenAI 是 prompt_cache_key；Anthropic 显式 cache_control 断点——细节各家不同

杠杆二：模型路由（按任务分流，别一律用旗舰）

任务类型模型档位理由
闲聊、格式转换、简单分类便宜快速档（deepseek-chat 级）旗舰的智力是浪费
复杂推理、规划、Agent 决策推理档（flash/reasoning 级）4.9：值得用推理的场景=想的比写的多
embedding / 批量处理专用便宜模型 + 批处理接口（半价）对延迟不敏感的任务换价格

实现可以很简单：const model = task.difficulty === "hard" ? expensive : cheap;——一个 if 就是路由器。进阶才做"小模型先判断难度再分流"（那本身也是一次调用，别过度工程）。

杠杆三：上下文瘦身（5.5 的工程化复述）

  • 历史压缩（截断/摘要/结构化记忆）——5.5 三板斧直接用
  • 工具结果剪枝：老的工具输出替换成一句话摘要（5.5 Anthropic 长文的 compaction）
  • few-shot 瘦身：示例 2 个够就不放 5 个（每个示例每轮都在重发，除非吃到缓存）
  • 工具数量克制：每挂一个 tool，说明书 token 常驻每一轮
🔧 动手 6.5（轻量）在 6.3 的聊天应用（或控制台）里实测缓存经济学：固定 system（≥200 token 的规则文本）连发 5 次 → 记录每次 prompt_tokens / cached_tokens / 费用变化；然后每轮往 system 里追加一个变化的时间戳再发 5 次 → 看缓存全灭。两张表记进笔记，这就是你将来给老板讲成本的素材。
6.6

模型选型与思考模式

验收：选型的五个维度怎么权衡？何时开推理模型、effort 给多少？产出：毕业项目候选模型清单。
💡 钩子你已经用 body 摸过 flash（reasoning 吃光 max_tokens 那次）和 chat 的差别——这节把那种"体感"升级成"决策框架"。选型不是选"最好的模型"，是给你的任务光谱配一排合适的模型。

五个维度

思考模式：什么时候开、开多大

4.9 的结论直接复用：值得开推理模型的任务 = "需要想的"显著超过"需要写的"——数学、规划、Agent 的决策步、复杂调试。不值得：翻译、抄写、格式转换、闲聊（思考是纯浪费）。

  • 思考预算（effort）：OpenAI 系 reasoning_effort: "low"|"medium"|"high"；Anthropic budget_tokens；DeepSeek 系列多为自动（部分模型支持 max_tokens 内划分）。给多少：从 low 起，只在实测答不对时升级——high 的延迟和费用经常是 low 的数倍
  • Agent 场景的坑（你 5.4 会碰到的）：推理模型的思考也占上下文——每轮决策都思考的 Agent，token 消耗可能 3~5 倍于普通模型。常见架构： Agent 的"规划步"用推理模型（一次想清楚），"执行步"用普通模型（照办就行）——这就是 6.5 模型路由在 Agent 内部的应用
  • 你环境里的现实：你的 Key 现在被路由到 deepseek-flash——推理模型。做 6.3 聊天应用时注意：闲聊场景思考是浪费，观察 TTFT；如果体验太肉，看看你的厂商有没有非推理档可切

6.7

可靠性工程【浅】

验收（了解级）：四件套各防什么？指数退避是什么？为什么 LLM 应用比普通应用更需要降级预案？
💡 钩子你已经撞过的：网络超时（curl 那次）、finish_reason: length（思考吃光预算）。可靠性工程就是把"撞过才知道"变成"设计时就防"。
四件套防什么做法一句话
超时请求挂死占住资源fetch 的 AbortSignal.timeout（你已在用：60s）；流式单独给"首字节超时"（TTFT 卡死检测）
重试瞬时失败（429/5xx/网络抖动）指数退避 + 抖动 + 上限：1s→2s→4s（加随机抖动防惊群），最多 3 次就放弃。4 字头非 429 不重试（6.1 口诀）
限流你把厂商打爆 / 被厂商打回客户端令牌桶限速 + 读 429 响应头里的 retry-after 照办
降级主力模型不可用失败 N 次自动切备用模型/厂商（OpenAI 兼容协议的价值时刻：换 base_url 就切）+ 给用户的提示从"报错堆栈"变"稍后再试/已切换备用通道"
📝 为什么 LLM 应用更要降级普通应用的依赖（数据库/缓存）99.9% 可用性很正常；LLM API 的单模型可用性和延迟波动远大于传统依赖（过载、区域故障、静默限流），且你无法自愈只能等——所以"备用通道"不是奢侈是标配。你已经在实践了：你的厂商把请求静默路由到另一个模型名，某种意义上就是厂商层面的降级。
🔧 动手 6.7（可选，了解即可）在 6.3 聊天应用的 route.ts 里加一层最小重试：包一个 withRetry(fn, 3)——捕获 429/5xx，指数退避重试，其余错误直接抛。20 行以内。感受"重试逻辑住在 SDK 外面还是里面"的取舍（AI SDK 部分provider自带重试，自己包一层也是常见实践）。

Q1（6.1）错误码四大家族？哪些该重试？
400/422 请求不合格（改代码）、401/403 身份权限（改配置）、404 找不到（改配置查 /v1）、429/529 限流过载（重试）、5xx 服务端（少量重试+降级）。口诀：4 字头除 429 不重试——你的错重试还是错。
Q2（6.1）"换模型只改 base_url 和 key"的边界？
兼容的是协议形状不是能力全集：主干对话零成本；json_schema/reasoning 参数名/多模态各家名同实异；embedding 与专有端点不兼容。响应体 model 字段才是真相（你可能被静默路由）。
Q3（6.2）流式的 UX 价值本质是什么？
不减总时长，减首字时间 TTFT（30s 空白 → 2s 出字）——可感知进度决定用户去留；且长回答可边读边打断（省 token）。价值属于"人看"的场景。
Q4（6.2）流式 + 结构化输出怎么调和？
程序吃 JSON 不需要打字机效果——默认非流式；要透明就流式+尾端 parse（实验台做法）；要渐进填充才用 partial-json。你的 Agent 应用里只有聊天窗口值得流式。
Q5（6.3）AI SDK 四大件各替你抽了什么、没抽什么？
generateText=HTTP 拼装；streamText=SSE 全套；generateObject=Zod→JSON Schema+校验+重试（消灭 5.3 两份 schema）；tools+maxSteps=5.4 整个 for 循环。没抽：选模型、schema 设计、工具选择、失败策略——第 5 章教的正是这些。
Q6（6.3）为什么说"手搓过才学得会 SDK"？
SDK 抽象的是协议搬运苦活，出问题时你必须知道它底下在干什么才能排查（arguments 是字符串、SSE 边界、system 谁注入……）。抽象是租金，理解是本金——你已付过本金。
Q7（6.4）三种形态的本质区别？毕业项目怎么落位？
聊天=人驱动对话（历史为主）；副驾=上下文来自"用户正在做的事"；工作流=程序调用模型、人只在端点（结构化+可靠性是命门）。毕业项目三层叠加：外壳聊天 + 内核工作流（Agent 循环）+ 副驾式桌面上下文采集。
Q8（6.5）prompt caching 的条件与排列法则？
前缀逐 token 相同才命中（system/tools/few-shot 固定放前）；任何变化内容混进前缀缓存全灭。稳定的放前面，易变的放后面——5.5 法则的成本学版本。
Q9（6.6）何时开推理模型？effort 怎么给？Agent 内部怎么用？
想的比写的多的任务（规划/数学/Agent 决策）开；翻译抄写闲聊不开。effort 从 low 起步实测不够再升。Agent 内部：规划步用推理模型、执行步用普通模型（思考 token 也计费，全开 3~5 倍成本）。
Q10（6.7）重试的完整规则？为什么 LLM 应用必须降级预案？
只重试 429/5xx/网络错；指数退避+抖动+上限（如 1s/2s/4s 最多 3 次）；读 retry-after。LLM API 波动远超传统依赖且你无法自愈——降级（切备用模型/厂商）是标配不是奢侈，OpenAI 兼容协议让"切 base_url"成本趋零。
