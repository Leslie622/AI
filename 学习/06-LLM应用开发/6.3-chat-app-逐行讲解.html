全景：两个进程，一次请求的旅行

先立地图：Next.js 应用 = 前端（浏览器里的 React）+ 服务端（Node 进程里的 API Routes）。你的 Key 住在服务端。
一次请求的旅行：useChat POST → route.ts 转协议+循环 → DeepSeek / data 文件 → SSE 事件流回浏览器逐字渲染

对照 5.4 实验台：那边是 浏览器 → server.ts → 模型 的三层；这边是 浏览器 → Next API Route → 模型——架构完全同构，只是 server.ts 换成了 route.ts。

route.ts —— 服务端心脏，逐段讲

POST /api/chat：收 UIMessage[] → 转协议 messages → streamText（内含工具循环）→ 回 SSE 流。

① 模型配置（三行 = 你的 .env 三件套）

const deepseek = createOpenAI({
  baseURL: process.env.LLM_BASE_URL ? ... + "/v1" : "https://api.deepseek.com/v1",
  apiKey: process.env.LLM_API_KEY ?? "",
});
const MODEL_ID = process.env.LLM_MODEL ?? "deepseek-chat";
对照first-call 的 BASE_URL / API_KEY / MODEL 三常量，一字不差搬过来。注意 DeepSeek 要 /v1 后缀（它的 base 是裸域名的协商问题——你 first-call 里是代码拼 ${BASE_URL}/chat/completions 所以没感知，AI SDK 是 ${baseURL}/chat/completions，所以 baseURL 必须含 /v1）。?? "" 兜底：Key 没配时请求会发出去然后吃 401——错误码四大家族（6.1）的第一课。

② 工具定义（5.4 的说明书 + 执行器合体）

const read_file = tool({
  description: "读取 data/ 目录下的文本文件，返回内容。只允许 data/ 内的文件。",
  inputSchema: z.object({ filename: z.string().describe("文件名，如 todo.md") }),
  execute: async ({ filename }: { filename: string }) => {
    const safe = path.basename(filename);       // ← 5.4 同款白名单防线
    try { return readFileSync(path.join(process.cwd(), "data", safe), "utf8"); }
    catch (e) { return `读取失败：${...}`; }      // ← 5.4 教训：失败也回喂
  },
});
对照5.4 的 tools[] 数组（description + JSON Schema parameters）+ execReadFile() 函数，合成了一个对象。Zod schema 替你生成给模型看的 JSON Schema——5.3"两份 schema 手写两遍"的问题在这里被消灭。版本坑：ai v7 把字段名从 parameters 改成了 inputSchema——网上教程大多还是旧名，照抄会类型报错（我就是这么踩的）。process.cwd() = Next dev server 的启动目录 = chat-app 根，所以 data/todo.md 放工程根下。

③ POST 处理器：三步

export async function POST(req: Request) {
  const { messages }: { messages: UIMessage[] } = await req.json();

  const result = streamText({
    model: deepseek(MODEL_ID),
    system: "你是桌面助手，回答用中文。需要读文件时调用 read_file 工具。",
    messages: await convertToModelMessages(messages),
    tools: { read_file },
    stopWhen: stepCountIs(5),
  });

  return result.toUIMessageStreamResponse();
}
  • UIMessage[]：前端 useChat 维护的消息格式——每条消息是 parts[]（文本块/工具块混排），比协议 messages 多 UI 元数据。这是 SDK 的前端协议，不是模型的协议。
  • convertToModelMessages()：UI 协议 → 模型协议（5.1 的 messages 剧本）的翻译层。v7 里它返回 Promise，要 await（我踩的第二个坑）。等价于你自己写一个 messages.map(...) 拆 parts。
  • streamText(...)：立刻返回（不阻塞），内部开始流式生成。如果模型发了 tool_calls，SDK 在内部替你跑 5.4 的整个 for 循环：执行 execute() → role:"tool" 回喂 → 重新请求 → 直到模型 stop 或 stopWhen 触发。stepCountIs(5) = 你的 MAX_ROUNDS=5 保险丝。
  • toUIMessageStreamResponse()：把内部事件流打包成 SSE Response（Content-Type: text/event-stream）——你 server.ts 里那套 SSE→ndjson 翻译器的地位，只是方向反过来：它发给前端的是"UI 事件流"（text-delta / tool-input-available / tool-output-available…），前端 useChat 能直接消化。
对照收拢route.ts 全文 50 行。你手搓的等价物：first-call 的 fetch 拼装（~20 行）+ server.ts 的 SSE 翻译（~60 行）+ 5.4 的 runAgent 循环（~70 行）≈ 150 行。SDK 抽掉的正是这 150 行协议搬运；留下给你的决策：system 写什么、给哪些工具、白名单防线、轮数上限——第 5 章教的就是这些。

page.tsx —— 前端聊天界面，逐段讲

useChat 一行拿到全套状态机；你只负责把 parts 渲染成人话。

① useChat：前端状态机（你还没手搓过的那一块）

const { messages, sendMessage, stop, status, error } = useChat();
对照如果手搓，你需要的全部家当：messages（=你每轮重建的剧本的前端半边）、sendMessage（=POST /api/chat + 流式接收 + 增量更新 state）、stop（=你 6.2 学的 AbortController.abort）、status（"submitted"/"streaming"/"ready"，驱动按钮切换）、error（=try/catch 的友好版）。五件套 = 一个聊天 UI 的全部状态，useChat 打包给了你。它默认 POST 到 /api/chat——和你的 route.ts 约定俗成。

② 消息渲染：parts 是核心新概念

{messages.map(m => (
  <div key={m.id}>
    {m.parts.map((p, i) => {
      if (p.type === "text") return <div>{p.text}▍</div>;   // 流式光标
      if (p.type.startsWith("tool-")) return <div>🔧 工具调用…</div>;
      return null;
    })}
  </div>
))}
  • 消息 = parts 数组：一条 assistant 消息可以"先调用工具、再说一段话"，在 UI 上就是 tool 部件和 text 部件混排——你 5.4 页面上"意图报文 + 最终回答分开展示"的体验，就是 parts 结构支撑的。
  • 流式渲染：SSE 每来一个 text-delta，useChat 内部更新最后一条消息的最后一个 text part——React 重渲染，你看到逐字出现。你在 page.tsx 里看不到任何"接 SSE"的代码——全在 useChat 的 transport 里（默认 fetch-based transport，就是 6.2 说的 fetch-event-source 的封装）。
  • 工具部件：p.type 形如 tool-read_file，p.state 走 input-streaming → input-available → output-available——正是 5.4 四步的前端视角。我们渲染成"🔧 工具调用 read_file ✓ 完成"一行。

③ 停止按钮：一行

{busy ? <button onClick={() => stop()}>停止</button> : <button type="submit">发送</button>}
对照stop() 内部就是 AbortController.abort()（6.2）——中断 fetch，服务端 SSE 断开，streamText 感知到 abort 停止生成。已生成的 token 已计费（usage 已产生），半截消息留在界面上。

④ 样式

全部内联 style（不引入 Tailwind/CSS Modules，学习期少一层）。想美化随便改——布局逻辑：flex 纵向三段（标题/消息列表 flex:1 滚动/输入框）。

自检

读完能答上吗

Q1 为什么 Key 必须放 route.ts 而不能放 page.tsx？
page.tsx 在浏览器执行——代码和 env 都会被发给用户；route.ts 在 Node 进程执行，env 留在服务端。5.3 立的纪律在 Next 的文件路由里有了物理边界：app/api/ 下的文件在服务端，其余默认在客户端。
Q2 stopWhen: stepCountIs(5) 对应你手搓的什么？谁在循环内？
= 5.4 的 MAX_ROUNDS=5 保险丝。循环体在 SDK 内部：tool_calls → execute() → 回喂 → 重新请求，直到模型 stop 或步数到 5。你的代码只提供每轮的"执行器"（execute）。
Q3 UIMessage 和 ModelMessage 的区别？谁负责转？
UIMessage=SDK 前端协议（parts 混排、带 id/state）；ModelMessage=5.1 的模型协议（role/content/tool_calls）。convertToModelMessages() 负责转（服务端收请求时）。响应方向由 toUIMessageStreamResponse() 打包回 UI 事件流。
Q4 前端怎么知道工具执行了？p.state 有哪些态？
SSE 事件流里带 tool-input-available / tool-output-available 事件，useChat 把它们变成消息里的 tool 部件；state 走 input-streaming → input-available → output-available——5.4 四步的前端视角。
Q5 route.ts 50 行替代了你手搓的约多少行？没替代的是什么？
≈150 行（fetch 拼装 + SSE 翻译器 + Agent for 循环）。没替代的：system 文案、工具选择与白名单防线、轮数上限、模型选型——决策层全是你的。
